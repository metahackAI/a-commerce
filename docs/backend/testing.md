# 테스트와 평가

세 층으로 "작동한다"를 확인합니다. 아래 층일수록 빠르고 많고, 위 층일수록 느리고 적습니다.

| 층 | 무엇을 | 어디서 | 언제 |
|---|---|---|---|
| 1. 단위·계약 | 상태기계, 정책 체크, 혜택 계산, 오퍼레이션 하나의 입력→출력·에러·프리뷰 | `crates/*/tests`, `#[sqlx::test]` | 모든 PR |
| 2. 시나리오 재생 | 데모 시나리오를 **모델 없이** 정해진 툴 호출 순서로 재생하고 DB를 읽어 확인 | `crates/testkit`, `tests/scenarios/` | 모든 PR |
| 3. 에이전트 평가 | 실제 모델로 과업 세트를 돌려 지표 측정, 화면형 파사드와 대조 | `cargo xtask eval`, `eval/` | 수동·야간 |

---

## 1. 계약 테스트

- 오퍼레이션마다: 정상 입력의 출력 형태, 명세에 적힌 에러 코드 각각, 쓰기라면 프리뷰가 상태를 바꾸지 않는다는 것과 같은 `preview_id`로 두 번 실행해도 결과가 같다는 것.
- 출력 형태는 insta 스냅샷으로 고정합니다. 스냅샷이 바뀌는 PR은 명세([../api/](../api/README.md))도 같이 바꿔야 합니다.
- 레지스트리 전체 검사(`cargo xtask check-docs`): 명세 인덱스의 모든 툴 이름·주소·종류·REST가 레지스트리와 같은지, 구현 안 된 것은 목록으로 출력. 모든 입력 스키마가 닫힌 형식인지(추가 필드 금지, `$ref`·`anyOf`·`oneOf` 없음, 모든 필드 설명·예시).
- 정책 파일 검사: 모든 YAML이 타입으로 파싱되는지, 체크 키가 오퍼레이션 메타의 `checks`와 맞는지.

## 2. 시나리오 재생

[../scenarios.md](../scenarios.md)의 장면마다 테스트 하나. 데모 시드를 넣고 데모 시계를 장면 시각으로 맞춘 뒤, 사람이 썼을 툴 호출 순서를 HTTP로 재생합니다(에이전트 없이). 확인은 응답이 아니라 **DB를 다시 읽어서** 합니다.

예: VIP 주말 세일 변경셋

1. `search_products` → 여름 아우터 상품 수 확인.
2. `set_sale_prices`(프리뷰, 변경셋에 붙임) → 체크 결과가 장면의 기대값과 같음(하한에 걸리는 상품, 재고 미달 제외).
3. 대화 수정에 해당하는 재프리뷰 → 변경셋 v2.
4. `create_coupon`, `schedule_banner` 프리뷰 → `submit`.
5. 사람 전용 `approve {version: 2}` → 실행기 → `verify_change_set`이 전부 일치 → `live`.
6. 데모 시계를 토요일로 → 쇼퍼 시나리오에서 같은 상품의 회원가가 그대로 나옴(운영자가 정한 가격 = 쇼퍼가 보는 가격).
7. `undo` → 가격·쿠폰·배너가 모두 원래대로.

시나리오 테스트는 에이전트 평가의 정답지도 됩니다(같은 장면, 같은 기대 DB 상태).

## 3. 에이전트 평가

[../design.md](../design.md) §7의 실험입니다.

- **과업 세트:** `eval/tasks/{design,held_out}/*.yml`. 과업 = 면(bo/fo) + 페르소나 + 데모 시계 + 사람의 말(필요하면 여러 턴) + 기대 DB 상태 + 허용되는 툴 순서. 설계 세트는 개발 중에 보고, 보류 세트는 마지막에만 돌려 그 숫자만 README에 씁니다.
- **두 툴 레이어:** 같은 백엔드 위에
  - A-Commerce 툴(레지스트리 매니페스트)
  - 화면형 파사드(`acom-facade`): [../design.md](../design.md) §2의 패턴(화면 단위 엔드포인트, 축약 이름, 코드값, POST 읽기와 별도 카운트, 행 상태 플래그가 있는 일괄 저장, 버전 중복)을 **우리가 직접 쓴 일반적인 예**로 재현한 툴 목록. 같은 도메인 서비스를 부르므로 결과 데이터는 같습니다.
- **같은 런타임:** 에이전트 런타임은 매니페스트만 바꿔 끼웁니다. 툴 검색·계획·실행 코드는 같습니다.
- **모델:** Glimmer, Spark 각각.
- **지표:** 과업 완료율(기대 DB 상태와 일치), 툴 선택 정확도(올바른 툴·순서), 과업당 단계·모델 호출·툴 호출·비용, 반복 일관성(같은 과업 k회 실행의 pass^k).
- **결과:** `eval/results/{date}-{model}-{toolset}.json`과 요약 표. 원자료(턴 로그)는 `agent.model_call`·`agent.step`에서 내보냅니다.
